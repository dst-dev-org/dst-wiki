# DST 通用 Wiki 与模组 Wiki 的经验归属

2026-10-13 当前分发职责与安装方式以 [四仓决策](repository-split.md) 为准；下面保留此前取舍的演进依据，日常工作流由已安装 Skill提供。

记录 2026-10-10 的设计讨论，2026-10-11 随起步／道具／手部／身体护甲／头部 cookbook 交付更新范围，供后续建设第二个 Skill 和调整经验沉淀流程时回查。这是项目建设决策，不是游戏行为证据。2026-10-13 已明确为 dst-mod-dev-skill：模组开发是主职责，本地 Wiki 只是一个功能；共享查询／维护归 dst-wiki-skill。自包含边界见 [分仓决策](repository-split.md)。

## 职责与归属

经验按适用范围归属，保存在 Wiki 页面中；Skill 负责查询与维护流程，入口不装载全部案例和坑。

共享知识按用途分两层：`wiki/cookbook/` 保存通用组装任务，`wiki/reference/` 保存组件／Prefab／状态机与公共 API 机制。经验和源码证据可共同支持两层内容，验证要求相同；具体布局见 [结构决策](knowledge-base-structure.md#任务与机制两层布局)。

| 内容 | 归属 |
|---|---|
| 跨模组通用的模组起步、新增物品／角色／生物／植物／建筑、配方及功能接入的最小骨架 | 当前项目 `wiki/cookbook/`，提供组装上下文和机制扩展入口 |
| 原版接口限制、通用开发陷阱 | DST Wiki 相关页的“常见陷阱与限制”章节；跨页面问题在主要页面维护一份并互链 |
| 能跨模组复用的机制方案、开发案例与用法教程 | DST Wiki 相关组件／Prefab／状态机／API 页的“典型接入”章节；跨页实现选主要页面维护一份并互链 |
| 某模组专属的骨架、目录／注册约定、公共工具、实际实现、取舍与影响范围 | 该模组自己的代码仓与 Wiki |
| 开发中遇到的问题、修复过程与实际测试结果 | 先进入该模组自己的 Wiki |
| 尚未证实的猜测与实验 | 模组 Wiki 的待核验记录，不作为通用事实 |

- 共享知识 Skill 回答“怎样造新东西，原版怎么实现，有什么通用机制与限制”；cookbook 内容保存在 Wiki，Skill 只负责按需查询与维护，不在入口复制 demo。
- 模组开发 Skill 回答“这个模组怎么实现，为什么这样设计，改动影响哪里”，并维护开发产生的项目知识。
- 模组特有行为以其当前代码和核验记录为依据；引用通用页不能替代对本地覆盖、配置或差异的确认。

## cookbook 层的范围与建设

恢复 cookbook 的设计定位：它是有限的通用任务骨架层，解决“从零造出一个东西，需要哪些文件、资源和接入”的组装问题；机制页解决“某个能力怎样工作与组合”。此前将所有教程收进具体页，避免了重复案例，却也限制了跨对象基础骨架的直接入口，因此收窄该限制，允许 cookbook。

当前实际交付如下；索引将模组起步固定为第一条，后续只登记已交付场景，不预建空页：

```text
wiki/cookbook/                 # W05 按真实任务逐步建设
├── index.md                  # 短任务导航，不含代码
├── mod-starter.md            # 已交付：模组起步与加载验证
├── new-item.md               # 已交付：可拾取物品
└── equipment/               # 按制作场景拆分，当前只建已交付页
    ├── index.md             # 短导航
    ├── hand.md              # 已交付：手部装备
    ├── body-armor.md        # 已交付：身体护甲，穿戴图可选
    └── head.md              # 已交付：头部装备，穿戴图可选
```

每页以适用条件、最小 demo、按需求扩展、边界与验证四块组织，格式只在 [页面格式](../../../dst-wiki-skill/references/maintain/write-format.md) 维护。最小是满足所声明场景的必要上下文，不等于只有一段 Prefab 函数；资源未提供或不能取得时须明确缺口，不称完整可用。训练知识可以提供候选，不能替代当前版本的源码／已核验 Wiki 和必要运行记录。

cookbook 只保存基础组装及必要代码，扩展采用“需求 → 机制页章节”链接，不重写组件字段、方法表或完整机制实现。组装／加载／资源相关问题留骨架页，机制限制链接具体页；同一复用代码保留一个维护来源，确需共享文件时明确文件与取得方式，不让必要上下文藏在长链接链里。食物、装备等与道具有交集时可以链接其共用基础，是否保留独立页取决于实际差异和读取效果，不强求八类全部写成。

装备按手部／护符／身体护甲／头部装备／服装／背包的组装差异拆页，统一短导航只登记已交付内容。类别、实际槽位与功能能力分开；头部骨架扩展护甲、背包骨架扩展减伤，不为组合另造页。已知类别直达，无需逐层读索引；完整必要工厂保留叶级页，共用注册与机制只链接所需章节。多装备栏兼容核验实际版本／配置，不能仅靠槽位常量判断；模式与边界见 [手部](../reports/w05/hand-equipment.md)／[身体](../reports/w05/body-armor.md)／[头部检视](../reports/w05/head-equipment.md)。人物穿戴图作为显示选项，省图不删除组件功能或功能回调；身体与头部页仅短述，统一角色显示策略留后续角色骨架。

起步页只提供必要 modinfo／modmain、所选全局读取代理、运行端选择和加载检查；主 demo 不带测试 print／空回调，加载检查使用游戏原有日志。[modinfo 主题](../../wiki/reference/api/modinfo/index.md) 在 reference/api 下聚合字段、配置／名称和模式，起步页仍直达所需配置章节。各场景的项目骨架在对应页提供；完整 API 说明、资源格式与动画／美术制作在具体主题维护，起步页不展开所有目录。已有项目直接选所需场景，无需重新读取起步页。

骨架的普遍性通过真实任务验证，不称一个角色／生物／植物 demo 覆盖所有行为。先做道具、装备、配方、建筑四类试点；三个角色模组的入口梳理支持后续角色、容器、组件同步、主动技能与 HUD 等组装场景，具体顺序及依据在 [PLAN](../../PLAN.md#后续章节与推进顺序) 维护。机制单独查阅足以完成的场景不额外建骨架；不为每种附加效果组合创建新 cookbook，也不恢复 patterns／pitfalls／sessions 等独立目录。

## 经验提炼流程

1. 开发时先在模组 Wiki 记录问题、触发条件、实现／修复、源码依据、适用版本及验证结果；保留未解决范围。
2. 确认经验有跨模组复用价值后，显式发起整理到 DST Wiki，去掉项目专属名称和配置，保留通用前提、边界与证据。
3. 整理时确认本次已核验锚点与版本仍适用，证据缺失／版本不符或实现变化时补核验；一次问题记录不自动证明“常见”，源码审阅也不自动等于游戏运行通过。
4. 共享页维护通用部分，模组页链接它并保存自己的差异、采用版本和测试结果，避免复制后两处独立手改。

2026-10-12 新增 `/refine-dst` 的 [骨架维护入口](../../../dst-wiki-skill/references/maintain-skeleton.md)，用于显式整理通用组装经验，不要求工程环境；机制案例／陷阱仍走知识维护，项目专属实现仍归模组 Wiki。只在新增组装模式、必要上下文缺口或已核验冲突时增修，复用本次有效证据，不自动把每次开发产物写进共享库。

不要求每次模组开发同时更新两个库。共享库写入是明确的整理操作，不因模组 Wiki 自动维护而隐式获得授权；暂不建设自动双写或经验同步服务。

## 查询与 token 成本

新增对象／功能或修改涉及未知多文件组装时，先确认目标模组现有约定与项目专属方案，再从 cookbook 导航筛骨架，按需读 reference 扩展。骨架缺失／部分覆盖时，先查相关机制页，仍有证据缺口再定向查源码；有准确名称可直达，已有入口不读起步页。具体分支与停止条件见 [开发任务的读取顺序](layered-index-and-retrieval.md#开发任务的读取顺序)，不要求安装模组 Wiki Skill 或等待骨架生成。

修改现有模组时先查本地相关代码、短索引与页面；遇到原版接口、通用机制或证据缺口再查 DST Wiki，不默认经过 cookbook。纯原版问题可直接进入具体页。完成开发后，实际实现、采用版本、项目差异与测试记录归模组 Wiki，通用库不随编码自动写入。

两套 Skill 按任务加载，不默认同时读取两套维护规范、日志或全部知识。共享内容用链接与短摘要定位，读取选中的页面；本地差异影响通用结论适用时再补充证据。

## 对当前计划的影响

W01–W04 已完成，W05 已交付检索工具和起步／道具／手部／身体护甲／头部 cookbook，后续建设造物／功能骨架、页内机制案例与陷阱，验证“骨架 → 按需机制章节 → 源码缺口”的路线，并比较仅机制页与加入骨架后的正确性和读取成本。起步页仅源码审阅与结构／语法检查，游戏运行和真实任务成本尚未验证；开发 Skill 的独立初版流程随分仓交付，真实 harness和项目任务效果仍待验证。

曾考虑把全部经验集中到某一个 Skill，但那会混合通用规则与项目约定，增加查询噪声和维护成本，因此采用上述分工。

## 何时重新考虑

- 同一经验反复在多个模组出现时，评估提炼为共享方案。
- 骨架之间重复或必要上下文的链接链过长时，调整共用代码与页面边界；新增分类以实际差异和检索收益为依据。
- 模组页与共享页频繁重复或产生冲突时，调整通用内容和差异的边界。
- 实际查询出现漏读本地差异、加载两个库过多或版本难以追踪时，再设计联合检索与版本引用方式。
