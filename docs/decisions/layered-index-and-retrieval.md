# 分层索引与按需检索

2026-10-13 当前分发职责与安装方式以 [四仓决策](repository-split.md) 为准；下面保留此前取舍的演进依据，日常工作流由已安装 Skill提供。

记录 2026-10-10 确定的检索设计。这是项目建设决策，不作为 DST 行为证据。查询、日常增修与索引组织分别由 Skill 的 query.md、maintain/maintain-wiki.md 和 maintain/maintain-index.md 维护，本页保存理由、工具边界及后续验收方向。

## 目标与当前能力

服务新增物品、装备、建筑和修改已有机制两类任务。组件、Prefab 与方法数量大，根索引不能罗列全部条目；已知名称时逐层读索引也会增加无效读取。

当前已有 cookbook／reference 导航、模组起步骨架、三份组件页及 modinfo 三份接口页；inventoryitem 已作为道具骨架的必要机制先补齐。W03 已交付精简事实与 [源码查询](../../../dst-wiki-skill/references/query-source.md)，W05 已交付可选 Wiki 索引／查询与章节读取。造物骨架、暖石组合实现与真实任务三路成本比较仍待交付；结构测试及局部读取量不代表完整任务收益。

## 三条查询路径

| 请求特征 | 路径 | 读取范围 |
|---|---|---|
| 已知组件、Prefab、方法或其他标识符 | 直接查知识页路径／标识符；无页或证据不足时查源码符号 | 所选页面章节、定义与必要调用；跳过根／分类导航 |
| 描述要实现的功能 | 新增内容先确认项目约定，筛 cookbook 对应骨架；机制需求筛具体页摘要、别名、标识符与场景标题，排查读问题章节 | 少量候选 → 所需骨架／机制章节 → 接口与证据；骨架缺失时直接查具体页／源码 |
| 不清楚功能名称或想浏览方案 | 根分类 → 必要的主题层 → 叶级索引 → 所选页面 | 每次只展开相关分支；小分类可直接进入页面 |

路径可以切换：方案缺少某个接口依据时转为名称直查，关键词不明确时再浏览相关分类。歧义需要核对所属对象、场景与前提，不能仅凭同名选择实现。

没有 Python／可用缓存时，用 `rg --files` 找路径、`rg` 定向搜相关目录中的摘要／别名／标识符，再读取命中章节。Wiki 索引遗漏时仍搜索已有页面；需要源码兜底时按查询规则准备对应版本。只报告检索元数据不足以支持代码结论，还需读取所用证据。

## 开发任务的读取顺序

默认复用顺序是“目标模组已有实现／方案 → cookbook 组装骨架 → reference 机制／案例 → raw 源码缺口”。这是按子任务选择和回退的顺序，不要求每次读取所有层；执行摘要在 [查询规则](../../../dst-wiki-skill/references/query.md#查询)，本节保存具体设计，不作为普通查询的必读文件。

### 入口与分支

| 当前子任务 | 第一入口 | 后续路径 |
|---|---|---|
| 新建模组，目标尚无入口 | [cookbook 场景导航](../../wiki/cookbook/index.md) 中的 [mod-starter](../../wiki/cookbook/mod-starter.md) | 建立必要入口；配置、名称等功能只读所需 reference 扩展章节 |
| 在新／已有模组新增道具、装备、角色等对象或功能 | 先确认本地约定；有项目专属骨架先复用，否则从 cookbook 导航筛相应场景 | 核对骨架条件、文件／资源／加载位置；按子需求读扩展中的机制章节 |
| 修改需要新增注册、网络、UI 等尚不明确的多文件组装 | 本地实现确定改动边界，再筛 cookbook 相关接入骨架 | 复用所需组装部分，再补 reference 接口／案例；保留本地架构与已有行为 |
| 修改已实现的数值／行为或排查现有问题 | 本地相关代码／Wiki，随后直达相关 reference | 读接口、典型接入或陷阱；必要时查源码，不重建骨架或重读起步页 |
| 纯机制查询，或已有准确的组件／Prefab／方法／章节名 | 直接定位 reference 页面／章节 | 核对条件和证据，缺口转源码；跳过不需要的导航 |

`mod-starter` 的主要链接入口是所属 `cookbook/index.md`，读取链为 `AGENTS → SKILL → query.md → cookbook/index.md → mod-starter.md`（直接使用 Skill 可省 AGENTS）。query.md 只链接场景导航，不逐篇登记骨架；具体页的选择与适用摘要由所属索引维护。已知名称、搜索命中或 Top 30 可直达，属于快捷路径，不替代主入口。骨架页不反向加载规则、设计或计划；索引第一条只是浏览排序，不使起步页成为所有模组开发的前置。

### 命中、部分命中与回退

1. 将需求拆成新增／修改对象、效果、作用目标、生效条件与单位。判断哪些组装已有、哪些仍有缺口；已有项目代码是本地行为的依据，通用方案不能覆盖其自定义约定。
2. 需要组装时，在 cookbook 导航按需求与状态筛骨架。已知骨架可直达；导航增长时只筛相关分支，不读取所有页。读所选适用条件、完整必要 demo 和验证边界，再判断是否可复用，不凭标题直接套用。
3. 从骨架的“按需求扩展”只展开当前功能的 reference 章节，取得接口、副作用、案例与限制。链接是定位入口，章节内容仍需实际读取；没有链接不表示该能力不存在，也不要求必须有一篇完全相同的组合方案。
4. 没有适用骨架，或骨架只覆盖部分需求时，保留已适用部分，对缺口查 reference 的摘要／别名／标识符／场景标题。分类不明才读 [reference/index](../../wiki/reference/index.md) 选择组件、Prefab、状态机或 API 分支；已知主题直接进入相关页，不从根重新浏览。
5. reference 没有适用案例、证据不够，或版本／本地覆盖影响所用结论时，定向查该子需求的源码定义、关键分支、宿主与必要调用。索引未登记、缓存过期、无命中或截断时先核对相关实际页面／同义措辞；有限检索失败不证明源码没有能力。
6. 在目标模组组装实现，核对共用持有者、生命周期、网络域、单位与撤销条件。已取得必要证据与上下文就停止扩展；保留未验证范围，开发不自动写共享 Wiki 或另一套模组 Wiki。

回退按缺口发生，可以同时使用骨架、几个机制章节和一段原版源码；无需整项需求逐层失败后才进入下一层，也不因一个扩展无命中而放弃全部已核验内容。源码准备仍按查询规则在会话首次检查，后续“回退”指读取实现，而不是到最后才准备源码。

### 懒加载与当前实现边界

每轮初始骨架与机制候选共用最多 5 个；只读选中章节及必要前提／验证边界，不默认展开所有扩展、全量分类或所有源码引用。版本与证据充分的已有结论可复用，缺口才追加源码；修改已有知识页仍先读全文。

这是 AI 的决策流程：当前 `query_wiki.py` 提供词汇检索与章节输出，不自动执行本地项目适配、cookbook 优先、链接跟读或多层回退。AI 可通过导航／直接路径／范围筛选实施该顺序，纯 Markdown 路径不需要 Python；结构检查通过不证明另一模型已经按路由执行或实际节省 token。

例如，空目录建立模组读起步页并按需补配置；已有角色模组新增背包先查本地注册约定与容器骨架（尚未交付时查 reference／源码），不重读 mod-starter；修改斧头次数直查 finiteuses 接入；新增随身恒温／发光／回精神道具保留物品骨架、按三个效果补机制与共同清理，不等待整套组合 cookbook。实际行为与成本验收留 W05。

## 导航层级与增长方式

| 层级 | 内容 | 增长时的处理 |
|---|---|---|
| 根索引 | cookbook／reference 两类入口及最多 30 条高频快捷链接 | 保持短导航，不扩展为全量条目；大小与 Top 30 规则由 Skill 规范维护 |
| 分类／主题索引 | 子主题入口及需求范围 | 单次读取过大或难以筛选时，按真实任务拆主题 |
| 叶级索引 | 页面入口、需求摘要、必要别名与状态 | 继续增长时再按需求拆分，避免一次加载整个大分类 |
| 知识页 | cookbook 通用任务骨架，或具体对象／接口的实现、机制案例、限制与证据 | 按需读取骨架及所用扩展章节；机制页按对象／接口主题分工，保留主案例地址与互链 |

例如组件积累后可按物品与容器、装备、生命与战斗等需求组织；这是拆分方向，不是现在要创建的目录。层数随内容确定，小分类无需额外主题层，单个主题也不能成为新的全量列表。

当前已按 [任务与机制两层布局](knowledge-base-structure.md#任务与机制两层布局) 归位：reference 内保留四种对象／接口分类，API 的 modinfo 三页共用主题目录。各索引只提供浏览入口；检索仍直接返回知识页／章节，已知名称和 cookbook 扩展跳过中间层，不因路径加深扩大读取预算。

每页在一个所属叶级索引登记，保持一个正式内容地址；Top 30 仅是跨分类的快捷链接，不替代正式登记。跨对象机制案例在主要页维护一份，cookbook 保存骨架并链接机制。首份骨架落地时补根分类入口，合适骨架可另入高频节；拆分更新父级、原链接及快捷入口，不为任意组合建方案分类。

行数与字符数只是读取规模的代理；不靠固定“页面数阈值”证明成本。W05 根据实际读取量、候选质量和任务结果决定拆分粒度。

### 高频入口与页面规模

此前根只列分类，现在按用户需求增加 Top 30 高频快捷节，用少量“需求 → 页面／章节”减少常用任务的中间导航。只链接真实存在且有效的页面，先注明人工精选依据，有实际任务统计后再按记录调整；不凭源码引用频率宣称开发查询频率。当前人工精选起步骨架与三份组件页，不造排名或空链接。执行规则见 [索引维护](../../../dst-wiki-skill/references/maintain/maintain-index.md#top-30-高频入口)。

生成／维护的知识页和导航需要可执行的大小约束，初始行数与 UTF-8 字节双上限统一在 [页面格式](../../../dst-wiki-skill/references/maintain/write-format.md#文件大小)。cookbook 为完整 demo 留更大预算，超限先去重／按主题拆分，必要代码与证据不截断，实际生成器与校验器在 W04／W05 落实；当前可直接量取文件，不要求普通用户安装 Python。

根导航有 30 条入口不表示模型读取 30 个目标，查询仍定向选择少量章节。W05 比较加入快捷节前后的命中、导航读取量、根额外成本和完整结果，并验证上限能发现超长行／大代码块；阈值是初始工程约束，实测不足时在唯一规范调整。

## 两种独立索引

| 索引 | 输入与范围 | 返回内容 | 工作项 |
|---|---|---|---|
| 源码符号／引用索引 | Full Moon 的精简事实，可在试点验证后全量构建 | 文件、对象／作用域、符号、定义区间与必要引用，保留未解析项及覆盖信息 | W03 |
| Wiki 知识检索索引 | 已维护知识页的元数据与必要摘要，按真实需求精选 | 页面路径、需求、条件、状态、版本和证据入口 | W05 |

源码索引回答“定义和引用在哪里”，知识索引回答“哪些方案适合当前需求”。二者关联证据入口，不复制整份 AST、源码或实现；源码全量解析不自动产生几千份知识页。Wiki 的选中方案仍可通过源码索引补足证据。

第一版使用简单可重建文件，不引入完整 codegraph、图数据库或向量服务。只有轻量定义／引用与关键词筛选的实际效果不足时，才重新评估。

## 候选检索的边界

W05 首轮工具归 `scripts/tools/wiki/`：`update_index.py` 校验人工分层导航和页面后构建知识缓存，`query_wiki.py` 在工具内部过滤，read 实际输出章节行区间。人工 Markdown 决定分类／摘要／Top 30，构建器不重写导航；早期自动生成导航的设想调整为检查人工导航＋生成缓存，避免覆盖需求分类。LLM 只接收有限结果，不先加载整个 JSON、整个分类索引或所有页面。缓存 version 1 在忽略的 output 下可重建，包含元数据、明确标识符／条件、章节范围、哈希和覆盖，不复制完整代码或 AST。

候选最少包含：

- 路径、标题、需求摘要及命中的别名／标识符。
- 适用条件、页面状态、已核验的 build 与验证程度。
- 相关章节与证据入口，供下一步读取。

摘要与别名取自已维护元数据；章节来自明确标题，条件与标识符来自正文明确记录，不能凭文件名或标签猜行为。页类型保留以区分任务骨架和机制候选；cookbook 是已核验知识，不与未审校写作模板一并排除。首轮不新增必填条件字段：取前提／职责与适用／边界等明确条目和 cookbook 适用条件节，缺失报未知；词汇命中仍需读具体章节判断条件。

默认最多返回 5 个候选，并限制单项摘要长度；参数可调，初始预算在 W05 测量后调整。除候选外，结果需要说明：

- 查询范围与排序／匹配依据；同名或多方案歧义。
- 是否截断及能否继续缩小条件／追加候选。
- 实际索引覆盖、构建依据与是否落后于页面或源码；无法确认时报告未知。
- 无命中发生在何处，下一步应扩大 Wiki 搜索还是定向查源码。

不默认纳入决策、日志、会话、写作模板、AST 和未审校注解；归档页面仅在明确请求历史内容时返回，待复查页显示状态。候选摘要不是证据，页面已核验版本也不能自动代表当前源码版本。

无命中、空分类、结果上限、过期索引和解析失败均不能证明“没有实现”。关键词遗漏时补充同义需求或浏览相关主题；索引遗漏时搜索实际页面；覆盖不足或结论证据不足时转向源码。达到证据要求后停止扩展，不要求凑满候选数。

## 组合需求与章节检索

以“像暖石一样，在人物物品栏生效：物品恒温 35℃、持有者发光、精神每分钟增加 3”为设计验证场景。它需要通用物品骨架和多个机制，不能要求已有完全相同的案例。先分清对象、条件与单位，确认项目约定后取所需骨架，用原版参照定位机制，再补缺失能力；已有骨架或只问机制时跳过基础组装。

检索设计补充如下，有限词汇候选与章节读取已实现，真实组合内容仍留 W05：

- 新增物品按需进入 cookbook 道具骨架，扩展先读原版参照相关章节，再按“物品栏生效／无需装备／持有者发光／持续回精神”检索缺口；不默认读全部扩展链接，沿用摘要、别名与场景标题，不新增必填条件字段或关系图。
- 候选可定位到页内场景／接口章节，同一页的不同场景可以分别匹配。组合请求按子目标显示覆盖与缺口，每轮共享候选和输出预算，默认总计最多 5 个，不按子目标翻倍；证据不足时再定向追加，不要求读取全部候选页。
- 温度、发光、精神的接口分别核验，组合时再检查共同的作用对象、生效／失效条件、单位与清理。源码兜底须读必要消费者和宿主路径，仅知道 setter 或签名不足以完成实现。
- 可复用机制写相关组件／API 页的“典型接入”，原版暖石实例归 heatrock 页；跨对象实现由最相关具体页维护一次，其他页链接章节。不为这次尚未实现的设想建立独立方案页或虚构 Prefab 页。

组合实现候选应共用一次持有者／生效范围判定，再管理灯光与精神修饰，避免每种效果独立轮询；具体事件覆盖尚未完成，不将暖石的 onputininventory／ondropped 两个监听当作完整方案。开发前需明确主物品栏、背包、鼠标手持是否计入，多个副本能否叠加，以及 35℃所指对象。测试重点是放入／取出、转移箱子、背包脱卸、删除、重载、死亡／变幽灵与多份物品；温度组件实际还读取溢出容器和 activeitem（temperature.lua:391、:404），统一范围不能只凭名称推断。

这次场景暴露的是组合与生命周期知识的缺口。AST／类型适合定位符号与确认接口，场景选择和共同清理仍需要已核验正文；先用短章节和需求措辞补足，不扩展完整 codegraph。

## 验收与重新考虑

W05 使用同一组新增内容和机制修改需求，对比直接查源码与 Wiki 路径；记录命中、正确性、读取量、上下文 token、工具调用和未解决范围。分别统计一次性知识生成成本与重复查询成本；无法取得准确 token 时注明字符／行数代理，不预设节省比例。

新增任务还对比“只有机制页”与“cookbook 骨架＋所需机制章节”，检验文件／资源／加载上下文是否齐全、是否漏查项目差异及实际读取成本。机制查询和已有内容修改应能跳过 cookbook；骨架与机制候选共享每轮预算。详细范围见 [cookbook 决策](shared-and-mod-wiki.md#cookbook-层的范围与建设)。

验证已知名称不会强制读导航，描述需求能够召回适用方案，浏览只展开相关分支；还要覆盖大分类、同名、索引遗漏／失效、无命中和截断，确认这些情况不会被解释成实现不存在。

曾考虑只用分层导航，但它对已知名称增加中间读取；只用搜索则缺少探索入口且容易漏掉需求措辞，所以保留两者并按请求选择。暂缓向量检索、复杂排序、完整图分析和固定目录树，先检验轻量方案。

- 摘要／别名仍无法覆盖真实措辞时，先补充它们，再评估排序与其他检索方式。
- 主题层仍需大量读取时，调整拆分、结果预算和章节定位。
- 关系查询无法靠定义／引用回答时，评估更强关系索引及其维护成本。
- 新方案只有实测改善召回、正确性或读取成本后，才替换现有路线。
